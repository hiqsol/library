# Dark Code: The Organizational Crisis Nobody Is Talking About

Nobody understands their own code anymore. There is code running in production at
companies we use every day that nobody can really explain — not the engineer who shipped
it, not the team that owns the service, not the CTO. The code works, passes tests, but no
human fully understands what it does, why, or what happens if it stops.

The industry calls this *dark code* — code that was never understood by anyone because it
was generated by AI, passed automated checks, and shipped. The comprehension step simply
didn't happen, not from carelessness, but because the process no longer requires it.

## Why Dark Code Is Multiplying

Two reasons interplay to make things worse:

1. *Structural*: AI-generated code is inherently harder to understand because you didn't
   write it yourself. Unless you're disciplined with non-functional requirements, the
   comprehension gap is built in.

2. *Velocity*: AI enables moving fast. The pressure is to move fast. When you combine
   velocity with a structural reason not to understand code, comprehension decouples from
   authorship.

## Why Obvious Responses Don't Work

### Observability doesn't equal comprehension

Instrumenting every service gives you telemetry — you can measure what dark code is
breaking in production. That's great, but it's still dark code. You can observe the damage
without understanding the cause.

### Agentic pipelines add layers, not understanding

Having excellent orchestration and guard rails reduces risk, but adding layers to an agent
pipeline doesn't solve the dark code problem — it just means you now have to troubleshoot
multiple things when something goes wrong.

### The YOLO approach

Factory.ai's thesis: accept dark code exists and compensate with extraordinary testing and
eval discipline. This is a genuine hypothesis, but most organizations yoloing code into
production aren't nearly as disciplined. The result: nobody owns the sustained total
package of code in production because authorship is distributed.

## AI's Strengths Mask Its Weaknesses

The stronger AI models become, the easier it becomes to say "it's fine, the AI will fix
it." But it's hard to know when AI is overconfident. Even AI-native companies (Anthropic,
OpenAI) don't assume AI is magical — they still demand legibility and comprehension from
engineering teams alongside heavy investment in evals, pipelines, and telemetry.

## Layoffs Compound the Problem

When companies lay off engineers and expect the rest to do even more with AI, they create
more dark code. This isn't just an engineering problem — it touches SOC 2 compliance,
encryption standards, and business liability at the board level.

## What Actually Works: Three Layers

### Layer 1: Force Understanding Before Code Exists (Spec-Driven Development)

Write out what you want to build in enough detail that you can put it on paper — then go.
Not 16 artifacts of process, not zero thought. Just enough comprehension to own what
you're building.

After Amazon's December outage, they rebuilt their coding tool Kiro with exactly this
concept — the tool leads with spec-driven development, turning prompts into requirements
and task lists before generating code. The spec becomes the eval: a clear spec defines the
test the agent keeps trying to pass.

### Layer 2: Make Systems Self-Describing (Context Engineering)

Restructure your codebase so comprehension is embedded in the code itself. Three aspects:

- *Structural context* (where): Every module should have a manifest describing what it
  does, what it depends on, and what depends on it.
- *Semantic context* (what): Interfaces need rules of engagement — performance
  expectations, failure modes, retry semantics, behavioral contracts.
- *Comprehension context* (why): Make trade-offs and design decisions explicitly legible
  to both humans and agents.

### Layer 3: The Comprehension Gate

Put a comprehension filter in front of code reviews. Surface the questions a senior
engineer would ask: Why this dependency? Why this caching strategy? How are you thinking
about separation of concerns?

This creates a flywheel: the gate makes code readable and accountable, and the insights
feed back into better evals and higher-quality generation.

## Who This Matters For

- *Engineering leaders*: Table stakes questions are observability and pipelines. The real
  question: do you have mechanisms to make dark code legible?
- *Founders*: Knowing your code is both a competitive moat and a risk mitigator. You can
  stand out just by understanding what you ship.
- *Vendors*: Ask about dark code. Ask how much shipping companies understand what they
  ship.
- *Junior engineers*: The comprehension gate is an accelerator — it teaches you the
  questions senior engineers ask, making code less dark.
- *Senior engineers*: You can't avoid using AI to help review at volume. You need lenses
  on code that let you see more, farther, clearer.

## The Bottom Line

Nobody's going to slow down. Shipping before you fully understand what you've built is a
fixable problem, but not by going back to the old way. AI is helping us speed up, and we
should speed up. But going fast imposes new requirements for understanding code shipped at
speed — a different class of problem than the old human-mediated approach.

Dark code is an organizational choice. You can fight it. Choose to do so.
